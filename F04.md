# F04 - COMUNICACIÓN Y CONTROL DE HARDWARE

Esta funcionalidad representa el puente tecnológico entre la lógica digital de AUTOPASS y los componentes físicos (barreras, sensores y actuadores). Permite que el sistema tome decisiones basadas en software y las ejecute en el mundo real.

## 1. COMPONENTES DEL SISTEMA

El ecosistema de control de hardware se divide en cuatro capas principales:

### A. NÚCLEO DE COMUNICACIÓN (BACKEND INFRAESTRUCTURA)
Es el encargado de gestionar el protocolo de red que entiende el hardware.
- **Archivo:** [core/mqtt.py](file:///C:/xampp/htdocs/AUTOPASS/core/mqtt.py)
- **Función:** Inicializa el cliente MQTT utilizando la librería `paho-mqtt`. Configura la conexión con el Broker (intermediario) y define cómo se publican los mensajes de comando a través de [get_mqtt_client](file:///C:/xampp/htdocs/AUTOPASS/core/mqtt.py#L5).
- **Relación:** Depende de [core/config.py](file:///C:/xampp/htdocs/AUTOPASS/core/config.py) para obtener la dirección IP, puerto y credenciales del servidor de mensajería desde la clase [Settings](file:///C:/xampp/htdocs/AUTOPASS/core/config.py#L6).

### B. ORQUESTADOR DE LÓGICA (BACKEND RUTAS Y SERVICIOS)
Es el "cerebro" que decide cuándo enviar una orden al hardware.
- **Archivo:** [routes/parking/access.py](file:///C:/xampp/htdocs/AUTOPASS/routes/parking/access.py)
- **Función:** Contiene el endpoint `/access/validate-plate`. Cuando la IA o el lector QR confirma un acceso válido mediante la clase [AccessService](file:///C:/xampp/htdocs/AUTOPASS/services/access_service.py#L12), este archivo publica en el cliente MQTT el comando `OPEN`.
- **Archivo:** [routes/admin/operations.py](file:///C:/xampp/htdocs/AUTOPASS/routes/admin/operations.py)
- **Función:** Contiene la función [open_barrier](file:///C:/xampp/htdocs/AUTOPASS/routes/admin/operations.py#L11) que gestiona los comandos de apertura manual enviados por los operadores desde el panel de control.
- **Servicio de Notificación:** A partir de la versión v9.1.5, se integra [NotificationService](file:///C:/xampp/htdocs/AUTOPASS/services/notification_service.py) para disparar de forma paralela notificaciones en tiempo real del estado de aforo a los clientes web.

### C. DISPOSITIVO IOT (HARDWARE FÍSICO)
Es el componente que recibe la señal y realiza el movimiento mecánico.
- **Archivo:** [Info proyecto/Hardware/firmware_esp32.ino](file:///C:/xampp/htdocs/AUTOPASS/Info%20proyecto/Hardware/firmware_esp32.ino)
- **Ubicación:** Directorio de recursos de hardware.
- **Función:** Código C++ que corre en placas ESP32. Se conecta al Broker MQTT y se suscribe a los canales de control. Al recibir el comando `OPEN` en formato JSON, acciona un servomotor o relé para levantar la barrera y activa un sensor ultrasónico para detectar el paso del vehículo antes de cerrarse automáticamente.

### D. INTERFAZ DE OPERADOR (FRONTEND)
Es donde ocurre la interacción humana con el hardware.
- **Archivo:** [static/js/modules/dashboard-ui.js](file:///C:/xampp/htdocs/AUTOPASS/static/js/modules/dashboard-ui.js) y [static/js/modules/dashboard-admin.js](file:///C:/xampp/htdocs/AUTOPASS/static/js/modules/dashboard-admin.js)
- **Función:** Captura los eventos de clic en los botones de apertura manual y realiza peticiones asíncronas (`fetch`) a la API de administración para disparar el comando MQTT correspondiente.

## 2. FLUJO OPERATIVO (TRAZABILIDAD)

La secuencia de ejecución de F04 sigue este camino:

1. **ENTRADA DE DATOS:** El servicio ALPR ([alpr_service.py](file:///C:/xampp/htdocs/AUTOPASS/alpr_service.py)) detecta un vehículo y envía la patente o el código QR mediante HTTP POST a la API del backend.
2. **TOMA DE DECISIÓN:** La capa de servicios ([AccessService](file:///C:/xampp/htdocs/AUTOPASS/services/access_service.py#L12)) valida el vehículo (soporte trimodal: Auto, Moto, Camioneta) contra las reservas activas y el aforo actual de la sede en la base de datos.
3. **PUBLICACIÓN DEL COMANDO:** Si el ingreso o salida es autorizado, el backend invoca a la función de publicación en [core/mqtt.py](file:///C:/xampp/htdocs/AUTOPASS/core/mqtt.py), enviando un mensaje JSON a los tópicos de control:
   - Entrada: `parking/barrera/entrada/control`
   - Salida: `parking/barrera/salida/control`
4. **RECEPCION DE EVENTO DE USUARIO (TIEMPO REAL):** En paralelo a la publicación MQTT, el servidor notifica los cambios de aforo mediante WebSockets a todos los navegadores conectados.
5. **RECEPCIÓN IOT:** La placa ESP32 (o Arduino Wi-Fi) recibe el mensaje a través del broker MQTT casi instantáneamente.
6. **ACCIÓN FÍSICA:** El firmware lee el comando `"OPEN"`, muestra la patente y la bienvenida en la pantalla LCD, y acciona el servomotor a 90 grados.
7. **CIERRE Y RETROALIMENTACIÓN:** El sensor ultrasónico HC-SR04 mide la distancia. Una vez que el vehículo ha pasado la línea (distancia mayor a 20 cm), la barrera se cierra automáticamente a 0 grados y se reporta el estado al broker.

## 3. RELACIÓN CON OTROS MÓDULOS CORE

- **RELACIÓN CON F01 (PERSISTENCIA):** Cada evento de ingreso/salida y comando de apertura manual se registra en la tabla [AccessLog](file:///C:/xampp/htdocs/AUTOPASS/models/parking.py#L24) para auditoría financiera y operativa.
- **RELACIÓN CON F02 (ALPR):** La barrera es el actuador final del procesamiento de imágenes realizado por el motor OCR de visión computacional.
- **RELACIÓN CON F05 (SEGURIDAD):** El endpoint de apertura manual `/admin/open-barrier` requiere validación JWT y verificación de rol del operador (`get_operational_user`).
- **RELACIÓN CON F06 (AFORO - OPTIMIZACIÓN v9.1.5):** La autorización de acceso modifica los aforos correspondientes. Gracias a los WebSockets implementados en `/parking/ws`, los cambios de aforo y ocupación real se sincronizan al instante en el dashboard del operador sin necesidad de recargar la página.

## 4. NOTAS TÉCNICAS PARA EL ESTUDIO

- **PROTOCOLO:** Se utiliza MQTT por su muy baja latencia, robustez y bajo consumo de red, ideal para entornos de red inalámbrica inestable.
- **DESACOPLAMIENTO:** Si el broker MQTT o el microcontrolador están desconectados, el backend de la API sigue respondiendo normalmente y reporta un estado "OFFLINE" en los diagnósticos del dashboard de salud del sistema, permitiendo la operación por contingencia humana sin detener la facturación.
- **DEPENDENCIAS CLAVE:**
  - Librería Python: `paho-mqtt`
  - Entorno WebSockets: `fastapi.WebSocket`
  - Librerías C++ (ESP32): `PubSubClient`, `ESP32Servo`, `LiquidCrystal_I2C`, `ArduinoJson`
