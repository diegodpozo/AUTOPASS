FLUJO DE DATOS PASO A PASO

                    
COMO SE COMUNICA LA BASE DE DATOS CON EL PROGRAMA

                

            

        


        

            LA COMUNICACION ENTRE EL PROGRAMA PYTHON (FASTAPI Y SERVICIOS DE VISION) Y LA BASE DE DATOS SIGUE UN CIRCUITO
            ESTRICTAMENTE CONTROLADO EN CAPAS. NINGUN CONTROLADOR ACCEDE AL MOTOR A CIEGAS; TODO VIAJA A TRAVES DE
            SESIONES AISLADAS, INYECCION DE DEPENDENCIAS Y EL PATRON REPOSITORIO:
        


        


            
            

                
1

                

                    
DISPARO DEL EVENTO: SOLICITUD WEB O DETECCION DE CAMARA

                    

                        EL RECORRIDO COMIENZA CUANDO UN NAVEGADOR HACE UN PEDIDO HTTP (POR EJEMPLO, CREAR UNA RESERVA EN /API/RESERVATIONS/)
                        O CUANDO EL HILO DE VISION ARTIFICIAL (OPENCV) RECONOCE UNA PATENTE EN EL VIDEO DE ENTRADA Y DISPARA EL INGRESO DEL AUTO.
                    

                    

                        ARCHIVOS:
                        routes/reservations.py
                        alpr/core.py
                    

                

            


            
            

                
2

                

                    
INYECCION DE DEPENDENCIAS: CREACION DE SESION LIMPIA (GET_DB)

                    

                        FASTAPI INVOCA LA FUNCION GENERADORA GET_DB() DEFINIDA EN CORE/DATABASE.PY.
                        ESTA FUNCION TOMA UNA CONEXION PREPARADA DEL POOL DE SQLALCHEMY, ABRE UNA SESION AISLADA (DB = SESSIONLOCAL())
                        Y SE LA ENTREGA AL CONTROLADOR MEDIANTE DEPENDS(GET_DB). SI OCURRE UN ERROR O CUANDO EL ENDPOINT TERMINA,
                        EL BLOQUE FINALLY: DB.CLOSE() CIERRA LA SESION Y DEVUELVE LA CONEXION AL POOL SIN DEJAR RECURSOS ABIERTOS.
                    

                    

                        ARCHIVOS:
                        core/database.py
                        core/config.py
                    

                

            


            
            

                
3

                

                    
CAPA DE SERVICIOS: LOGICA DE NEGOCIO Y VALIDACIONES

                    

                        EL ENDPOINT DERIVA LA TAREA AL SERVICIO CORRESPONDIENTE (EJEMPLO: RESERVATION_SERVICE.PY O ACCESS_SERVICE.PY).
                        ACA SE VERIFICAN LAS CONDICIONES: ¿HAY COCHERA DISPONIBLE EN EL AFORO? ¿EL VEHICULO TIENE MULTAS?
                        ¿EL CLIENTE DISPONE DE SALDO SUFICIENTE O PAGO CON MERCADO PAGO?
                    

                    

                        ARCHIVOS:
                        services/reservation_service.py
                        services/access_service.py
                    

                

            


            
            

                
4

                

                    
CAPA DE REPOSITORIOS: CONSULTAS ORM Y SEGURIDAD MULTITENANT

                    

                        EL SERVICIO NUNCA ARMA CONSULTAS A MANO; LLAMA A LOS REPOSITORIOS (EJEMPLO: RESERVATION_REPOSITORY.PY).
                        EL REPOSITORIO EJECUTA SENTENCIAS ORM COMO DB.QUERY(RESERVATION).FILTER(...).
                        ADEMAS, EL MODULO REPOSITORIES/SCOPING.PY APLICA AUTOMATICAMENTE EL FILTRO DE SUCURSAL PARA QUE NINGUN
                        OPERADOR DE UNA SEDE PUEDA LEER O MODIFICAR DATOS DE OTRA SUCURSAL.
                    

                    

                        ARCHIVOS:
                        repositories/reservation_repository.py
                        repositories/access_log_repository.py
                        repositories/scoping.py
                    

                

            


            
            

                
5

                

                    
MOTOR SQLALCHEMY: TRADUCCION A SQL NATIVO Y POOL DE CONEXIONES

                    

                        SQLALCHEMY TOMA EL MODELO DECLARATIVO DE MODELS/, VALIDA LOS TIPOS DE DATOS Y CONVIERTE LA CONSULTA
                        A SENTENCIAS SQL NATIVAS (SELECT, INSERT, UPDATE) OPTIMIZADAS PARA EL MOTOR ACTIVO.
                        UTILIZA PARAMETRIZACION ESTRICTA, HACIENDO IMPOSIBLE CUALQUIER ATAQUE DE INYECCION SQL.
                        EL POOL GESTIONA 20 CONEXIONES PERMANENTES (CON CAPACIDAD DE DESBORDE DE HASTA 40) Y EJECUTA PINGS PREVIOS
                        PARA COMPROBAR QUE LA CONEXION CLOUD CON NEON EN SAO PAULO SIGA VIVA ANTES DE ENVIAR LA CONSULTA.
                    

                    

                        ARCHIVOS:
                        models/__init__.py
                        models/parking.py
                    

                

            


            
            

                
6

                

                    
BASE DE DATOS RELACIONAL: TRANSACCIONES ACID Y INTEGRIDAD

                    

                        EL MOTOR DE BASE DE DATOS (POSTGRESQL O SQLITE) EJECUTA EL COMANDO. SI SE TRATA DE UN ALTA (INSERT)
                        O MODIFICACION (UPDATE), SE APLICA EL DB.COMMIT(). SI CUALQUIER VALIDACION FALLA EN EL MEDIO,
                        SE DISPARA DB.ROLLBACK() DEJANDO LA BASE DE DATOS EXACTAMENTE EN EL ESTADO ANTERIOR, SIN CORRUPCIONES NI REGISTROS HUERFANOS.
                    

                    

                        BASE DE DATOS:
                        POSTGRESQL NEON (NUBE)
                        PARKING.DB (LOCAL)
                    

                

            


            
            

                
7

                

                    
SERIALIZACION Y RESPUESTA FINAL

                    

                        LOS OBJETOS RETORNADOS POR LA BASE DE DATOS SE CONVIERTEN EN ESQUEMAS PYDANTIC TIPADOS Y SALEN EN FORMATO JSON
                        HACIA LA INTERFAZ WEB, O EMITEN UN MENSAJE POR WEBSOCKET / SSE PARA QUE LA BARRERA VIRTUAL SE LEVANTE EN PANTALLA.
                    

                    

                        ARCHIVOS:
                        schemas/ (PYDANTIC)
                        core/mqtt.py

MODELO ENTIDAD RELACION

                    
MAPA DE VINCULACIONES ENTRE TABLAS

                

            

        


        

            LAS 18 TABLAS DE AUTOPASS SE ORGANIZAN EN 6 GRUPOS MODULARES CONECTADOS MEDIANTE CLAVES FORANEAS (FOREIGN KEYS)
            QUE ASEGURAN QUE NO EXISTA INFORMACION HUERFANA Y QUE TODO REGISTRO ESTE RESPALDADO:
        


        


            
            

                

                    1. ORGANIZACION Y SEDES
                    INFRAESTRUCTURA
                

                

                    ●
                    ORGANIZATIONS: EMPRESA MATRIZ DUENA DEL SISTEMA.
                

                

                    ↳
                    PARKING_BRANCHES: SUCURSALES (CENTRAL, CASTELAR, MORON, ITUZAINGO).
                

                

                    ↳
                    PARKING_FLOORS: PISOS O SECTORES INTERNOS POR SEDE.
                

                

                    ↳
                    SETTINGS: TARIFAS Y REGLAS DE TIEMPO GLOBALES O POR SUCURSAL.
                

            


            
            

                

                    2. USUARIOS Y VEHICULOS
                    ACCESO Y ROLES
                

                

                    ●
                    USERS: ADMINISTRADORES, ENCARGADOS DE SEDE Y CLIENTES.
                

                

                    ↳
                    VEHICLES: AUTOS, MOTOS Y CAMIONETAS VINCULADOS A CADA USUARIO.
                

                

                    ↳
                    USER_SESSIONS: REGISTRO DE TOKENS, IPS Y DISPOSITIVOS ACTIVOS.
                

            


            
            

                

                    3. CONTROL DE ACCESOS Y VISION
                    OPERACION ALPR
                

                

                    ●
                    PARKING_CAMERAS: CAMARAS ASIGNADAS A CARRILES DE ENTRADA O SALIDA.
                

                

                    ↳
                    ACCESS_LOGS: CADA EVENTO DE PASO DETECTADO CON FOTO, HORA Y ESTADO.
                

                

                    ↳
                    PARKING_AFORO: CONTADOR EN TIEMPO REAL DE PLAZAS LIBRES Y OCUPADAS.
                

            


            
            

                

                    4. RESERVAS Y FINANZAS
                    MONETIZACION
                

                

                    ●
                    RESERVATIONS: APARTADO DE COCHERA POR FECHA, PATENTE Y TIPO DE ESTADIA.
                

                

                    ↳
                    MERCADOPAGO_PAYMENTS: PAGOS DIGITALES CON CHECKOUT PRO Y WEBHOOKS.
                

            


            
            

                

                    5. FIDELIZACION Y CANJES
                    BENEFICIOS
                

                

                    ●
                    PROMOTIONS: BENEFICIOS DISPONIBLES (DIAS LIBRES, LAVADOS, CAFES).
                

                

                    ↳
                    REDEMPTION_TICKETS: CUPONES Y TICKETS CON QR GENERADOS POR CLIENTES.
                

                

                    ↳
                    POINTS_LOG: HISTORIAL DE PUNTOS GANADOS Y CONSUMIDOS POR USUARIO.
                

            


            
            

                

                    6. ATENCION Y MENSAJERIA
                    SOPORTE
                

                

                    ●
                    SUPPORT_TICKETS: CONSULTAS Y RECLAMOS DE CLIENTES A LA ADMINISTRACION.
                

                

                    ↳
                    SUPPORT_TICKET_MESSAGES: CONVERSACION Y ADJUNTOS EN CADA TICKET.
                

                

                    ↳
                    USER_NOTIFICATIONS: ALERTAS IN-APP Y AVISOS DE ENTRADA, SALIDA Y PAGOS.
