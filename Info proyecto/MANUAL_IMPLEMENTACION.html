1.Descripción del sistema

1.1 Objetivo

AUTOPASS es un sistema de gestión integral de estacionamientos. Centraliza el registro de ingresos y egresos vehiculares, la reserva de lugares por parte de los usuarios, el cobro de suscripciones mediante pasarela de pago y el control físico del acceso mediante barreras operadas a distancia.

El sistema se apoya en reconocimiento automático de patentes (ALPR) mediante cámara y microcontrolador para registrar los movimientos sin intervención manual, y expone un panel de administración con métricas de ocupación, reportes y gestión de usuarios. El mismo conjunto de datos alimenta tanto el portal de usuarios como el back-office administrativo.

La regla de negocio central del proyecto es el aforo solo físico: el campo de ocupación refleja únicamente los vehículos efectivamente estacionados. Una reserva garantiza la disponibilidad de un lugar, pero no descuenta aforo hasta que el vehículo ingresa.

1.3 Arquitectura general

El sistema es un monolito modular de capas, ejecutado por un único proceso Python bajo Uvicorn. La lógica se separa estrictamente en capas para que cada una tenga una única responsabilidad:

HTTP / WebSocket ──▶ routes/ (FastAPI: endpoints, validación, HTTP) │ ▼ schemas/ (Pydantic: contratos de entrada y salida) │ ▼ services/ (lógica de negocio e integraciones externas) │ ▼ repositories/ (acceso a datos, consultas SQL) │ ▼ models/ (tablas SQLAlchemy) │ ▼ core/ (configuración, BD, seguridad, seed)

El frontend se sirve server-side: las vistas son plantillas Jinja2 renderizadas por el backend y estilizadas con CSS/JavaScript estático. No hay una SPA ni build step, por lo que el despliegue consiste únicamente de código Python más archivos estáticos.

El reconocimiento de matrícula funciona como proceso auxiliar independiente (alpr_service.py), que se comunica con el servidor principal. Ambos pueden ejecutarse por separado, lo que permite desplegar el ALPR en una máquina con cámara y el servidor web en otra.

3.Preparación del entorno

Esta sección describe la preparación de una computadora o servidor desde cero. Cada paso indica qué hacer y cómo verificar que se realizó correctamente.

3.1 En Windows (ruta recomendada)

  1. Instalar Python 3.14
    Descargarlo de python.org/downloads. En el instalador, marcar “Add python.exe to PATH”.
    Verificar: en una terminal nueva, python --version → debe imprimir Python 3.14.7 o superior de la misma rama.
  2. Instalar Git
    Descargarlo de git-scm.com (o winget install Git.Git).
    Verificar: git --version → debe mostrar el número de versión.
  3. Obtener el código fuente
    Seguir la sección 4. El repositorio es privado: hay que solicitar acceso previo al propietario del proyecto.
    Verificar: dentro de la carpeta del proyecto debe existir main.py y requirements.txt.
  4. Ejecutar el instalador

    Doble clic en setup_backend.bat. El script crea el entorno virtual, instala las dependencias e inicializa la base de datos.
    Verificar: el instalador debe terminar mostrando [OK] en cada etapa, y debe existir la carpeta venv\. Si falla, la causa suele aparecer arriba del mensaje de error.
  5. Iniciar el servidor
    Doble clic en run_server.bat, que abre automáticamente el navegador en la aplicación.
    Verificar: abrir http://localhost:8000 → debe cargar la pantalla de acceso. Logs: Uvicorn running on http://127.0.0.1:8000.

6.Configuración de variables de entorno

Toda la configuración se centraliza en un archivo .env en la raíz del proyecto. El archivo .env.example funciona como plantilla y debe copiarse a .env. Esta sección documenta qué variables existen y qué debe proporcionar el administrador; no incluye valores reales.

Qué trae la plantilla y qué hay que completar

La plantilla se distribuye con la cadena de conexión de la base de datos de desarrollo ya completa, para que el equipo trabaje sobre una base común sin pasos adicionales (ver el criterio del equipo en la sección 14). El resto de los valores sensibles se completan en la instalación: el token de MercadoPago, la contraseña del servidor de correo y los secretos de OAuth no viajan en el repositorio.

SECRET_KEY sí viene con un valor de ejemplo. Cada instalación debe reemplazarlo por uno propio y aleatorio: si se mantiene el valor de ejemplo, la seguridad de las sesiones depende de que el repositorio siga siendo privado.

Nunca publicar valores reales en la documentación

Las claves, contraseñas y tokens son datos sensibles. Este manual muestra únicamente placeholders. El archivo .env está excluido del control de versiones: nunca debe subirse al repositorio ni enviarse por correo sin cifrar.

7.3 Creación del esquema e importación de datos

El proyecto usa Alembic como gestor de migraciones. No existen archivos .sql sueltos: el esquema se construye ejecutando el inicializador, que además sincroniza el historial de migraciones. 

# INICIALIZACIÓN COMPLETA (comando principal)



venv\Scripts\python.exe init_db.py

Este único comando realiza tres acciones, en este orden:

  1. Crea el esquema mediante los modelos SQLAlchemy (create_all).
  2. Sincroniza Alembic: estampa todas las migraciones hasta el head (9c4f2a7b1e83), de modo que el estado declarado del historial coincide con el esquema real.
  3. Carga los datos iniciales (seed): usuarios y catálogos básicos necesarios para poder ingresar al sistema.
Comando de verificación

Debe imprimir el resumen de tablas creadas y los usuarios iniciales sembrados, sin excepciones.

7.4 Gestión de migraciones

ComandoFunción
python -m alembic currentMuestra la revisión aplicada actualmente.
python -m alembic historyLista el historial completo de migraciones.
python -m alembic headsMuestra la revisión head (la más reciente).
python -m alembic upgrade headAplica todas las migraciones pendientes.
python -m alembic downgrade -1Revierte la última migración aplicada.

El repositorio contiene 17 migraciones que evolutionan el esquema desde la creación inicial hasta el estado actual (índices de rendimiento, soporte de adjuntos, Promociones por ubicación, eliminación de una tabla obsoleta, entre otras). La revisión head es 9c4f2a7b1e83.

Copia de seguridad antes de migrar

En PostgreSQL, un pg_dump previo es obligatorio ante cualquier actualización de esquema: pg_dump -U usuario -h host autopass > respaldo_autopass.sql. Las migraciones que eliminan tablas son irreversibles.

10.Puesta en funcionamiento

Esta sección responde la pregunta fundamental: “si recibo el proyecto desde cero, ¿qué tengo que hacer para que funcione?”

10.1 Ruta completa en Windows (resumen)

  1. Instalar Python 3.14 y Git — sin ellos no hay intérprete ni forma de obtener el código.
  2. Solicitar acceso al repositorio — el repositorio es privado.
  3. Clonar el código — git clone https://github.com/MarianoJAC/AUTOPASS.git y entrar a la carpeta.
  4. Crear la configuración — copiar .env.example a .env.
  5. Completar las variables obligatorias — como mínimo SECRET_KEY (valor aleatorio nuevo) y DATABASE_URL (apuntando a la base definitiva, no a la del ejemplo).
  6. Instalar y preparar la base — ejecutar setup_backend.bat, que crea el entorno, instala dependencias e inicializa el esquema.
  7. Cambiar las contraseñas iniciales — los usuarios del seed comparten contraseña; es el primer paso obligatorio tras instalar.
  8. Arrancar el servidor — ejecutar run_server.bat.
  9. Acceder a la aplicación — abrir http://localhost:8000 e iniciar sesión.
  10. Configurar los servicios opcionales — pagos, correo, OAuth y barreras, si se necesitan (sección 9).
  11. Arrancar el reconocimiento de matrículas — solo si se va a usar: python alpr_service.py.

13.4 Procedimiento de diagnóstico

  1. Revisar la salida del servidor. El error real aparece en la terminal antes del mensaje genérico.
  2. Validar la configuración. venv\Scripts\python.exe -c "from core.config import settings; print(settings.VERSION)" — si falla, el problema está en .env.
  3. Validar la base de datos. venv\Scripts\python.exe -m alembic current — debe indicar la revisión head.
  4. Reinstalar desde cero. Eliminar venv\ y ejecutar setup_backend.bat: descarta la posibilidad de una instalación dañada.
  5. Revisar los logs del proceso ALPR si el problema es de reconocimiento de matrículas, por ser un proceso independiente del servidor web.

14.Seguridad de la información

Lista de verificación para que la implementación no introduzca fugas de información.

14.1 Antes de poner el sistema en producción

Obligatorio
  • Generar una SECRET_KEY propia y aleatoria. Compartir la de ejemplo anula la seguridad de las sesiones.
  • Cambiar la contraseña de todos los usuarios creados por el seed, que comparten una contraseña común.
  • Definir ALPR_NODE_SECRET, que por defecto está vacío.
  • Configurar DATABASE_URL con una base propia, nunca con datos de ejemplo.
  • Verificar que el archivo .env está excluido del control de versiones.
  • Servir el sistema por HTTPS.

14.2 Manejo de credenciales

Práctica correctaPráctica prohibida
Entregar las credenciales por un canal seguro y separado.Enviar contraseñas por correo sin cifrar.
Usar valores de prueba en la configuración de demostración.Incluir claves o tokens reales en documentación, código o tickets.
Rotar las credenciales al cambiar de servidor.Reutilizar las credenciales de un entorno en otro.
Mantener .env fuera del repositorio.Subir .env con valores reales.
Decisión del equipo: base de desarrollo compartida en la plantilla

Para que cualquier colaborador pueda levantar el proyecto sin pasos adicionales, el archivo .env.example se distribuye con la cadena de conexión de la base de datos de desarrollo ya completa, de modo que baste con copiarla a .env para empezar a trabajar. Es una decisión consciente del equipo y define el modelo de seguridad del proyecto: el acceso a la base está autorizado para todas las personas con acceso al repositorio.

Consecuencias asumidas y condiciones que la sostienen:

  • El repositorio debe permanecer privado. Es la condición principal: si el proyecto se publica o se distributesin control de accesos, la base queda expuesta.
  • Se trata de una base de desarrollo, no de producción. Los datos que contiene son descartables y no hay información sensible de usuarios reales.
  • La credencial es de escritura, por lo que cualquier collaborator puede modificar o borrar el contenido. Por eso el seed se puede reejecutar para reconstruir los datos iniciales.
  • Al concluir la cursada, la base y su credencial deben eliminarse o rotarse.

Lo que nunca debe distribuirse en el repositorio son las claves de servicios de terceros (token de MercadoPago, contraseña de SMTP, secretos de OAuth, SECRET_KEY): esas se entregan por un canal privado o se completan en la instalación.

14.3 Exposición de la aplicación

  • Uvicorn escucha en 127.0.0.1: no es accesible desde la red por defecto, lo cual es lo deseable.
  • Para exponer el sistema, usar un proxy inverso con TLS o el túnel de cloudflared, en lugar de abrir el puerto 8000 en el router.
  • El túnel de acceso remoto deja el sistema accesible públicamente: usarlo solo para demostraciones.
  • Las imágenes capturadas se sirven desde una ruta pública del servidor; revisar que su contenido sea appropriate.

14.4 Registro de auditoría

El sistema registra los accesos a la aplicación y los eventos relevantes en tablas de auditoría, que el administrador puede consultar desde el panel. Ante una investigación de seguridad, estos registros son la fuente de evidencia: no deben borrarse ni modificarse manualmente.
