DOCUMENTACIÓN DETALLADA DEL SISTEMA — AUTOPASS v9.2.0

Esta guía interactiva explica de manera minuciosa el rol, la lógica interna y las dependencias de cada archivo y componente del ecosistema AUTOPASS. Está diseñada para que cualquier persona, aun sin conocimiento previo del proyecto, comprenda cómo interactúan el software (FastAPI + Vanilla JS), la visión artificial (ALPR) y el hardware (ESP32).

¿CÓMO FUNCIONA EL SISTEMA? (RESUMEN CONCEPTUAL)

AUTOPASS es un sistema de gestión de estacionamientos inteligentes que funciona bajo un modelo de control por flujo. Cuando un auto llega a la barrera, el sistema de visión artificial lee su patente y decide si dejarlo pasar o no basándose en las reservas vigentes o el espacio disponible. Todo esto ocurre en milisegundos y de manera automatizada.

El Camino de un Vehículo (Flujo de Entrada Típico)

Detección de Presencia: El sensor físico del microcontrolador en la barrera de entrada detecta un vehículo o el sistema de video recibe el feed continuo.
Procesamiento ALPR: El servicio de visión artificial (alpr_service.py) toma los fotogramas de la cámara, localiza la patente mediante OpenCV, extrae el texto mediante EasyOCR y envía la patente normalizada al backend mediante una petición HTTP POST.
Validación y Negocio: El backend recibe la patente en el controlador de accesos (routes/parking/access.py) y delega la decisión al servicio de acceso (services/access_service.py). Este servicio verifica si el auto ya está adentro, si posee una reserva abonada o si hay cupo libre "al paso".
Apertura Física: Si el acceso es autorizado, el backend envía un comando "OPEN" al broker de mensajería MQTT (core/mqtt.py). El microcontrolador físico (ESP32) recibe este comando de forma instantánea y acciona el servomotor para levantar la barrera física.
Actualización en Tiempo Real: En paralelo, el backend calcula la nueva ocupación y la transmite mediante WebSockets (services/notification_service.py) a todas las interfaces web conectadas, actualizando el tablero de control del operador sin recargar la página.

ORGANIZACIÓN EN CAPAS (ARQUITECTURA LIMPIA)

Para mantener el código ordenado, extensible y fácil de mantener, el sistema se divide en 6 capas lógicas:

Core Infraestructura

Configuraciones base del sistema, comunicación con la base de datos física, cifrado de seguridad JWT y tokens, cliente para el broker MQTT de las barreras y llenado inicial de datos. Es la base sobre la que se apoya todo.

Data Modelos y Validación

Define la estructura de la base de datos relacional (tablas, columnas y relaciones mediante SQLAlchemy) y las reglas de validación para los datos de entrada y salida (esquemas de Pydantic). Evita datos corruptos.

API Rutas (Controladores)

Endpoints o URL expuestas del servidor FastAPI. Actúan como una capa de transporte muy delgada: solo reciben los datos, validan la identidad de quien llama (seguridad RBAC) y delegan la ejecución a la capa de servicios.

Servicios Lógica de Negocio

Aquí reside la inteligencia del negocio. Son clases y funciones dedicadas exclusivamente a procesar las reglas complejas del sistema: calcular tarifas, validar aforos trimodales, gestionar el ciclo de vida de las reservas y notificar eventos.

Frontend Interfaz de Usuario

La cara visible de la aplicación. Utiliza plantillas HTML renderizadas en el servidor (Jinja2), estilos CSS premium con efectos de transparencia (glassmorphism) y JavaScript modular (ES6) para la interactividad en tiempo real.

Tool Herramientas y Pruebas

Scripts auxiliares, repositorios de consultas específicas de base de datos, tareas de migración de datos y la suite de pruebas automáticas (tests unitarios con pytest) para garantizar que los cambios no rompan nada.

1. CORE — CAPA DE INFRAESTRUCTURA BASE

Ubicada en el directorio core/. Contiene los cimientos tecnológicos del backend.

  • Core core/config.py — Configuración Centralizada (Singleton settings)

    Este archivo se encarga de leer el archivo de configuración de entorno (.env) y cargar todas las credenciales, claves y constantes del sistema en un objeto único y seguro. Al actuar como un "Singleton", todo el sistema consulta esta misma instancia evitando lecturas repetidas del disco.

    Componentes clave:
    • Clase Settings: Define las variables requeridas y sus tipos.
    • Variable settings: Instancia global exportada para consumo general.     Variables críticas expuestas:
    • DATABASE_URL: Ruta del archivo de base de datos SQLite (ej. sqlite:///./parking.db).
    • SECRET_KEY: Llave criptográfica para firmar los tokens JWT de sesión.
    • RESERVA_HORA_MIN_SEGUNDOS: Tiempo de anticipación mínimo para reservas por hora (por defecto 3600 segundos = 1 hora).
    • Configuración del Broker MQTT (MQTT_BROKER, MQTT_PORT) para controlar las barreras.     Relación con otros archivos: Es importado por casi cualquier archivo que necesite saber una dirección IP, puerto, clave secreta o valor de tarifa base.
  • Core core/database.py — Motor y Conexión de Base de Datos (SQLAlchemy)

    Configura la comunicación con SQLite. Establece el "Engine" (puente de conexión), la clase base de la cual heredarán todos los modelos de tablas (Base) y el generador de sesiones de consulta (SessionLocal).

    Componentes clave:
    • SessionLocal: Fábrica de conexiones de base de datos.
    • Base: Clase declarativa base para mapear objetos Python a tablas SQL.
    • get_db(): Función generadora (yield) usada como dependencia en las rutas de FastAPI. Abre una sesión de base de datos cuando llega una petición HTTP y la cierra automáticamente al terminar, evitando fugas de memoria.
    • init_db(): Inicializa físicamente el archivo SQLite creando todas las tablas que hereden de Base si no existen en el disco.
  • Core core/security.py — Seguridad, Cifrado de Claves y Roles (RBAC)

    Es el guardián de la aplicación. Provee las herramientas para encriptar contraseñas antes de guardarlas, generar tokens JWT firmados cuando un usuario inicia sesión, y verificar si un token recibido es válido y qué permisos tiene el usuario.

    Componentes clave:
    • verify_password(plain, hashed): Compara una contraseña ingresada con su hash bcrypt guardado en base de datos.
    • get_password_hash(password): Encripta una contraseña usando el algoritmo seguro bcrypt.
    • create_access_token(data, expires_delta): Genera un token JWT de sesión con un tiempo de expiración determinado.
    • Filtros de Seguridad (Guards/Dependencies):
      - get_current_user: Valida que el llamador esté autenticado con un token válido.
      - get_super_admin: Exige que el usuario tenga rol de Administrador General (control de toda la red).
      - get_local_manager: Exige rol de Administrador Local o Administrador General.
      - get_operational_user: Exige rol de Operador (Staff), Administrador Local o Administrador General.     Flujo de Aislamiento: Las funciones de verificación comprueban la columna sucursal del usuario para asegurar que un Administrador Local no pueda ver ni modificar datos de una sucursal ajena.
  • Core core/mqtt.py — Cliente de Comunicación con Hardware (MQTT)

    Inicializa y configura el cliente de mensajería ligera MQTT (usando la librería paho-mqtt). El protocolo MQTT funciona bajo un modelo de publicación y suscripción muy rápido, ideal para enviar órdenes instantáneas de apertura a las barreras físicas.

    Componentes clave:
    • get_mqtt_client(): Configura y devuelve el cliente conectado al servidor (broker) definido en los settings.
    • Variable mqtt_client: Instancia de conexión persistente compartida en el ciclo de vida del backend.     Lógica física: Cuando un acceso es válido, el backend publica un mensaje JSON en el tópico parking/barrera/+/control. Las placas ESP32 de las barreras están suscritas a este tópico, reciben la orden y levantan el servomotor de inmediato.
  • Core core/seed.py — Datos Iniciales de Puesta en Marcha (Seeding)

    Contiene la información inicial necesaria para que el sistema funcione la primera vez que se crea la base de datos. Registra los usuarios administradores por defecto, las sucursales iniciales con sus respectivas coordenadas, las tarifas base y las promociones disponibles.

    Datos insertados:
    • Administrador Global: admin@autopass.com (Contraseña: admin123).
    • Administradores Locales para Morón, Ituzaingó y Castelar.
    • Sucursales activas con su información geográfica (latitud, longitud) y horarios de atención.
    • Tarifas configuradas por defecto en la tabla de configuraciones globales (settings).
    • Lista de promociones y beneficios canjeables por puntos de fidelidad.

2. MODELOS Y ESQUEMAS — CAPA DE DEFINICIÓN DE DATOS

Ubicada en models/ y schemas/. Define cómo se guardan los datos en la base de datos y cómo se validan al entrar o salir de la API.

  • Data models/enums.py — Tipado Seguro de Estados y Roles

    Define las enumeraciones (Enum) oficiales del sistema. Esto evita el uso de palabras mágicas escritas a mano (como escribir "pagado" en un lugar y "PAGADO" en otro), garantizando coherencia absoluta en la base de datos.

    Enumeraciones clave:
    • UserRole: Define los roles "admin", "local_admin", "staff" y "user".
    • VehicleType: Define los tipos de vehículos soportados: "Auto", "Moto" y "Camioneta".
    • AccessEventType: Tipos de tránsitos en barrera: "ENTRADA" y "SALIDA".
    • ReservationStatus: Estados de reserva: "Pendiente", "Activa", "Completada" y "Cancelada".
    • PaymentStatus: Estados de pago: "Pendiente", "Pagado", "Fallido", "Reembolsado" y "Cancelado".
  • Data models/user.py — Estructuras de Usuarios, Flotas y Puntos

    Contiene la definición de las tablas relacionadas con las personas y sus beneficios en el sistema.

    Tablas definidas:
    • User: Almacena DNI, nombre, email, hash de contraseña, rol asignado, sucursal a la que pertenece (si es administrador local), saldo de dinero digital y puntos de fidelidad acumulados.
    • Vehicle: Registra las patentes asociadas a los usuarios. Tiene una relación de clave foránea (user_id) apuntando a la tabla de usuarios. Incluye el tipo de vehículo para aplicar tarifas diferenciadas y una bandera is_favorite.
    • PointsLog: Registro histórico de sumas y restas de puntos de fidelidad acumulados por reservas o canjes.
    • Promotion: Catálogo de beneficios disponibles en el sistema de fidelización (título, descripción, costo en puntos, estado activo).
  • Data models/parking.py — Estructuras del Estacionamiento y Ocupación

    Define cómo se modelan las sucursales, los pisos y los registros de ocupación física.

    Tablas definidas:
    • ParkingBranch: Información de cada sede física (nombre, dirección, teléfono, coordenadas geográficas para el mapa interactivo y estado activo).
    • ParkingFloor: Soporte multi-nivel. Cada sucursal puede tener múltiples pisos, cada uno con capacidades de cupo independientes para autos, motos y camionetas.
    • ParkingAforo: Contador en tiempo real del aforo de cada sucursal. Registra la ocupación actual segregada por tipo de vehículo (autos, motos, camionetas) para no permitir ingresos si la capacidad máxima de ese tipo fue alcanzada.
    • AccessLog: Historial de todos los tránsitos por las barreras. Guarda la patente leída, tipo de evento (entrada o salida), tipo de vehículo, la sucursal, la hora exacta, el costo calculado de la estadía, si el pago fue confirmado, y la ruta de la fotografía del vehículo tomada por la cámara.
    • Settings: Tabla de configuración dinámica clave-valor para tarifas y parámetros del sistema específicos de cada sucursal.
  • Data models/reservation.py — Estructuras de Reservas y Cupones

    Mapea las reservas realizadas por la aplicación móvil y los códigos de descuento.

    Tablas definidas:
    • Reservation: Registra el usuario que reservó, la patente autorizada, fecha y hora de inicio y fin, tipo de estadía (por hora o estadías de período largo como día, semana, mes), monto total a pagar, identificador de pago de la pasarela y el estado actual de la reserva y del pago.
    • Coupon: Cupones de descuento que los usuarios pueden ingresar para reducir el monto total de su reserva (código único, porcentaje de descuento, fecha de vencimiento y estado activo).
  • Data schemas/ (Directorio) — Esquemas de Validación Pydantic

    Contiene las clases Pydantic encargadas de validar que los datos enviados por los clientes (JSON) cumplan con los formatos correctos antes de procesarlos en el servidor. Si un dato no es válido (por ejemplo, un email mal escrito o una patente con caracteres inválidos), la API lo rechaza inmediatamente con un error descriptivo.

    Archivos internos y sus validaciones:
    • schemas/auth.py: Valida formatos de inicio de sesión y restablecimiento de claves.
    • schemas/user.py: Valida el registro de usuarios. Obliga a que el DNI y el teléfono contengan solo números, que el teléfono tenga al menos 10 dígitos, y que la contraseña contenga una combinación segura de letras, números y caracteres especiales.
    • schemas/parking.py: Valida las lecturas de patente del ALPR y la estructura de los códigos QR.
    • schemas/reservation.py: Controla la creación de reservas (valida que la fecha de fin sea posterior a la de inicio).

3. ROUTES — CONTROLADORES Y ENTRADAS DE LA API

Ubicada en routes/. Contiene los endpoints (URL) expuestos por el servidor. Estas rutas son delgadas: no calculan precios ni deciden accesos, solo reciben datos y llaman a la capa de servicios.

  • API routes/auth.py — Endpoints de Autenticación Pública

    Gestiona el flujo de registro y acceso de los usuarios.

    Endpoints principales:
    • POST /v1/auth/register: Registra un nuevo cliente en el sistema y crea su vehículo favorito en un solo paso.
    • POST /v1/auth/login: Valida las credenciales del usuario y le devuelve un token JWT para sus siguientes peticiones.
    • POST /v1/auth/forgot-password: Genera un token temporal de recuperación y envía un correo electrónico al usuario mediante el servicio de email.
    • POST /v1/auth/reset-password: Valida el token temporal y actualiza la contraseña en la base de datos.
  • API routes/views.py — Renderizado de Páginas HTML (Jinja2)

    Es el encargado de servir la interfaz gráfica web de AUTOPASS. Lee las plantillas HTML del directorio templates/, procesa las variables dinámicas utilizando el motor Jinja2 y le devuelve el HTML completo al navegador del usuario.

    Particularidad técnica: Inyecta la instancia de settings en todas las plantillas. Esto permite que el frontend conozca el nombre del proyecto, el logo o la URL base configurados en el servidor de manera dinámica.
  • API routes/reports.py — Reportes Financieros y Auditoría

    Provee los datos necesarios para construir los gráficos de facturación e ingresos en el panel administrativo.

    Filtros avanzados implementados: Permite filtrar el historial financiero por rango de fechas exactas (calendario), tipo de vehículo (autos, motos, camionetas) y método de pago (caja, saldo digital, Mercado Pago). Regla de seguridad (Aislamiento): Si el usuario que consulta es un Local Admin, las consultas SQL se filtran automáticamente para devolver únicamente los datos de su sucursal asignada. Los administradores globales tienen acceso a los datos de toda la red.
  • API routes/system.py — Monitoreo de Cámaras y Diagnóstico del Servidor

    Controla el estado físico del servidor, el estado de los procesos de visión artificial y el streaming de video en vivo.

    Endpoints y WebSockets clave:
    • GET /health: Devuelve el estado de salud de la base de datos y el tiempo transcurrido desde el último latido (heartbeat) de las cámaras.
    • POST /camera-service/{gate_id}/{action}: Permite al administrador iniciar ("start") o detener ("stop") el proceso independiente de lectura de patentes (alpr_service.py) desde la interfaz web, ejecutándolo como un subproceso del sistema operativo.
    • WS /ws/video/{camera_id}: Canal de comunicación WebSocket bidireccional de alta velocidad. El servicio ALPR envía los fotogramas en formato JPEG codificados en Base64, y esta ruta los retransmite a los operadores para que puedan ver el video de la cámara en vivo en sus navegadores sin retrasos.
  • API routes/parking/ (Directorio) — Control de Accesos, Aforos y Notificaciones Push

    Contiene las rutas específicas para la operación del estacionamiento.

    Archivos y funciones destacadas:
    • parking/access.py: Expone el endpoint crucial POST /v1/access/validate-plate utilizado por las cámaras ALPR para validar ingresos de patentes, y /pay-stay para abonar la estadía antes de salir.
    • parking/status.py: Expone el WebSocket WS /v1/parking/ws. Utiliza la clase OccupancyManager para agrupar las conexiones de los navegadores web por sucursal. Cada vez que ingresa o sale un vehículo, se envía un mensaje WebSocket automático a los navegadores del personal de esa sede para actualizar los números de ocupación e ingresar el vehículo a la tabla de control al instante, eliminando el polling (consultas repetidas cada X segundos).
    • parking/utils.py: Contiene funciones de limpieza y formateo de texto, como normalizar patentes de entrada (ej: pasar "abc-123" a "ABC 123" o "ABC1234" a su formato Mercosur visual).
  • API routes/admin/ (Directorio) — Panel de Administración del Personal

    Agrupa las operaciones exclusivas del personal operativo y los administradores.

    Módulos y lógica administrativa:
    • admin/users.py: CRUD de usuarios de la sucursal. Los administradores locales pueden crear operadores (Staff) pero tienen bloqueada en el backend la posibilidad de crear administradores generales o locales ajenos.
    • admin/operations.py: Contiene las acciones manuales del operador:
      - Apertura manual de barreras (publica el comando "OPEN" en MQTT).
      - Ingresos y salidas manuales (en caso de que falle la cámara). La salida manual implementa una política de cortesía de 10 minutos sin cargo.
    • admin/branches.py: Permite configurar las sedes y definir la cantidad de pisos (multi-piso) con sus respectivos cupos para autos, motos y camionetas.
    • admin/settings.py: Permite modificar las tarifas dinámicas de la sucursal (precio de la hora, día, semana, mes) para cada tipo de vehículo.
  • API routes/user/ (Directorio) — Portal del Cliente (Reservas y Billetera)

    Endpoints consumidos por los clientes para gestionar sus cuentas y planificar sus accesos.

    Módulos destacados:
    • user/vehicles.py: Permite al cliente registrar sus vehículos personales y elegir su favorito.
    • user/reservations.py: Flujo de creación de reservas. Valida que la sucursal esté abierta en el horario elegido, que posea cupo libre y que la reserva por hora se realice con al menos 1 hora de anticipación.
    • user/balance.py: Permite al usuario recargar dinero en su cuenta y consultar sus estadías activas y su deuda acumulada en tiempo real.
    • user/fidelization.py: Permite canjear puntos acumulados por promociones de estacionamiento gratuito.

4. SERVICES — EL CORAZÓN DEL BACKEND (LÓGICA DE NEGOCIO)

Ubicada en services/. Aquí se toman todas las decisiones lógicas del sistema. Si necesitas modificar una regla de negocio o comportamiento, este es el lugar correcto.

  • Servicios services/access_service.py — Orquestador de Tránsito Vehicular (Entrada/Salida/QR)

    Gestiona el flujo completo de validación física en los accesos. Contiene la lógica trimodal (autos, motos, camionetas) y la integración con las barreras y las notificaciones push.

    Lógica detallada del método validate_plate(db, plate, gate_id) (Entrada):
    1. Normalización: Limpia la patente recibida de la cámara para asegurar coherencia en las búsquedas SQL.
    2. Control de duplicados: Verifica si el vehículo ya se encuentra dentro del estacionamiento para evitar lecturas dobles o ingresos erróneos.
    3. Detección vehicular: Identifica el tipo de vehículo (ej: las patentes que inician con una letra y tres números seguido de tres letras se categorizan como motocicletas en Argentina) para descontar del aforo correspondiente.
    4. Búsqueda de reserva: Busca en la base de datos una reserva pagada y vigente para esa patente en la sucursal actual.
    5. Evaluación de aforo según tipo de reserva:
      - Si tiene reserva de período largo (Día/Semana/Mes): El usuario tiene "libre tránsito". Puede entrar y salir libremente. El ingreso se autoriza sin descontar del aforo de paso, ya que su plaza fue reservada y descontada al momento de pagar la reserva.
      - Si tiene reserva por hora o entra "al paso" (sin reserva): El sistema verifica si hay plazas disponibles para su tipo de vehículo en el aforo actual. Si hay lugar, autoriza el ingreso e incrementa el contador de ocupación en el aforo.
    6. Registro y Apertura: Crea un registro en la tabla de accesos (AccessLog) con estado de pago pendiente (si entra al paso), publica la orden "OPEN" en MQTT para levantar la barrera física, y notifica a los dashboards vía WebSockets.     Lógica detallada del método exit_plate(db, plate, gate_id) (Salida):
    Verifica que el vehículo tenga un ingreso activo registrado. Comprueba que la estadía esté paga (o que posea una reserva vigente). Si está todo en orden, registra la salida en el historial y resta una unidad de la ocupación del aforo de la sucursal (excepto si es un usuario con reserva de período largo, cuya plaza permanece ocupada hasta que finalice su período de reserva).     Lógica del método validate_qr(db, qr_code, gate_id):
    Desencripta y parsea el código QR presentado en el lector. Extrae el identificador de la reserva y la patente del vehículo, y ejecuta el mismo flujo de validación de entrada o salida según corresponda.
  • Servicios services/reservation_service.py — Gestor del Ciclo de Vida de las Reservas

    Controla la creación, el pago con saldo de billetera virtual, las cancelaciones automáticas y los reembolsos proporcionales de dinero al usuario.

    Lógica del Aforo Diferenciado por Tipo de Reserva:
    • Reservas por hora: No ocupan lugar en el aforo físico de la sucursal hasta que el auto llega físicamente a la barrera de entrada.
    • Reservas de período largo (Día, Semana, Quincena, Mes): No pre-ocupan plaza en el aforo físico. La disponibilidad se valida contra los cupos exclusivos de reserva, y el aforo físico refleja solo los vehículos realmente presentes: el ALPR de entrada lo incrementa y el de salida lo decrementa. El cliente puede entrar y salir cuantas veces quiera durante el período sin que su plaza quede reservada ni bloqueada.     Lógica de reembolsos proporcionales:
    Si un usuario cancela una reserva antes de su inicio, recibe el 100% del dinero de vuelta en su saldo digital. Si cancela una reserva que ya está en curso (por ejemplo, una reserva mensual que va por la mitad), el servicio calcula los días restantes y le devuelve un reembolso proporcional directo a su cuenta, liberando su plaza del aforo al instante.
  • Servicios services/billing_service.py — Motor de Tarifas y Fidelización

    Contiene los algoritmos para calcular los precios de las estadías y gestionar la acreditación de puntos de beneficio.

    Cálculo de Deuda de Estadía (calculate_debt):
    Cuando un vehículo llega a la barrera de salida, el servicio calcula el tiempo transcurrido desde su entrada. Redondea el tiempo hacia arriba en fracciones de 1 hora (el mínimo a cobrar es 1 hora). Consulta las tarifas dinámicas vigentes de la sucursal y el tipo de vehículo (las motos tienen descuento, las camionetas un recargo) y devuelve el monto final a pagar.     Programa de puntos (Fidelización):
    Al completarse un pago de estadía o reserva, el método calculate_points() acredita automáticamente 10 puntos de fidelidad en la cuenta del usuario por cada $1000 abonados (monto / 100).
  • Servicios services/notification_service.py — Integración WebSocket con Hilos (v9.1.5)

    Es un servicio de infraestructura desacoplado. Permite que el servidor web principal envíe notificaciones en tiempo real a los dashboards de los operadores desde cualquier parte del código del backend, incluso desde hilos de ejecución secundarios o tareas de fondo.

    Solución técnica implementada:
    Dado que FastAPI ejecuta el servidor web y los WebSockets de forma asíncrona (asyncio), y la base de datos o ciertos procesos de fondo corren de forma síncrona en otros hilos, el servicio almacena el bucle de eventos (event loop) de Uvicorn al arrancar en main.py. Cuando ocurre un cambio de aforo, el servicio utiliza la función asyncio.run_coroutine_threadsafe() para inyectar de forma segura la tarea de transmisión WebSocket en el hilo principal del servidor, evitando bloqueos y caídas.
  • Servicios services/email_service.py — Generación de Correos Electrónicos Transaccionales

    Construye y envía correos electrónicos en formato HTML con diseños responsivos y elegantes (confirmación de reserva, recordatorios y restablecimiento de contraseña).

    Detalle técnico destacado:
    Cuando un usuario reserva, este servicio genera un código QR único en memoria (utilizando la librería qrcode de Python), lo codifica en formato Base64 y lo incrusta directamente en el cuerpo del correo electrónico HTML. El usuario puede mostrar este correo en la barrera para ingresar si la cámara no lee su patente, sin necesidad de descargar archivos adjuntos.
  • Servicios services/worker_service.py — Tareas en Segundo Plano (Daemon Thread)

    Al arrancar el servidor, este servicio inicia un hilo de ejecución secundario en segundo plano (Worker) que corre de forma infinita en ciclos de 5 minutos para mantener la base de datos limpia y actualizada.

    Tareas recurrentes automáticas:
    1. Cancelación de impagos: Llama a cleanup_overdue_reservations() para cancelar automáticamente reservas cuyo horario de inicio ya pasó hace más de 2 horas y no registran pago, liberando el cupo para otros clientes.
    2. Vencimiento de vigencias: Llama a auto_finalize_all_reservations() para expirar las reservas que alcanzaron su horario de finalización. Si son reservas de período largo, se encarga de liberar la plaza del aforo de la sucursal de manera automática.
    3. Envío de alertas: Envía correos de recordatorio a los usuarios que tengan reservas próximas a iniciar en los siguientes 30 minutos.

7. ARCHIVOS RAÍZ — ORQUESTADORES GENERALES

Archivos ubicados en la raíz del proyecto. Son los puntos de entrada para iniciar los servicios y la base de datos.

  • Core main.py — Punto de Entrada y Orquestador del Backend FastAPI

    Es el archivo principal que se ejecuta para iniciar el servidor web. Se encarga de instanciar la aplicación FastAPI, configurar las reglas de seguridad de intercambio de recursos (CORS) y montar todos los sub-routers de la API bajo sus respectivos prefijos (rutas de administración, usuarios, reportes, accesos, etc.).

    Eventos de inicio (Startup Event):
    1. Base de Datos: Llama a init_db() para verificar que la base de datos esté lista.
    2. Hardware: Conecta el cliente MQTT global (mqtt_client) al broker para dejarlo listo para enviar órdenes.
    3. WebSockets: Registra la instancia del gestor de ocupación (OccupancyManager) en el servicio de notificaciones.
    4. Hilo de fondo: Inicia el hilo secundario (Worker) que limpia reservas vencidas de forma asíncrona.
  • Servicios alpr_service.py — Motor de Visión Artificial (Proceso Standalone)

    Es un proceso de software independiente que se ejecuta de forma paralela al servidor web. Captura los fotogramas del feed de video de una cámara de entrada o salida y aplica algoritmos de procesamiento de imágenes y redes neuronales para leer caracteres.

    Flujo de procesamiento interno:
    1. Captura y cola: Lee los frames del stream de video y los coloca en una cola interna limitada a 4 elementos (maxsize=4). Si la cola se llena porque la cámara procesa a altos FPS, se aplica la política "drop-oldest", descartando el frame más antiguo para evitar latencia y congelamiento del video.
    2. Detección rápida de QR (Quick QR): Antes de procesar la imagen con el motor OCR (que es pesado para el procesador), realiza un escaneo rápido buscando patrones de códigos QR. Si detecta uno válido, envía el código al backend y salta el procesamiento de patente.
    3. Reconocimiento óptico (OCR): Si no hay QR, recorta la zona de la patente, mejora su contraste usando la librería OpenCV y extrae los caracteres con la red neuronal de EasyOCR.
    4. Consenso y Debounce: Para evitar falsas lecturas, requiere que el mismo texto de patente se lea de forma idéntica en varios frames seguidos. Una vez logrado el consenso, envía la patente al backend y activa un tiempo de espera (cooldown) de 10 segundos para esa patente, evitando registrar múltiples ingresos del mismo vehículo seguidos.
  • Tool init_db.py — Script de Creación e Inicialización Física de Base de Datos

    Un script de consola sencillo que se ejecuta al instalar el sistema. Se encarga de importar la configuración del motor de base de datos, borrar cualquier base de datos de pruebas anterior si se requiere, crear la estructura de tablas limpia y llamar a la siembra de datos maestros de core/seed.py.
